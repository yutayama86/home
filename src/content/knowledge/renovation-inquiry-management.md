Webフォーム、電話、LINEなど複数の受付経路を使っていると、問い合わせ情報が担当者のメールやメモに分かれます。問題は、ツールの数ではありません。「誰が対応中か」「次に何をするか」「見積後に連絡したか」を同じ基準で確認できないことです。

問い合わせ管理を整えるときは、新しいシステムを先に選ぶのではなく、受付から見積後フォローまでの流れと完了条件を決めることから始めます。

## 結論：問い合わせ管理は「一つの台帳」と「次回行動日」から整える

最初に行うのは、利用中の受付経路から入った案件を一つの案件台帳で確認できる状態にすることです。そのうえで、各案件に担当者・案件状態・次回行動日を設定します。

自動化の対象は、受信確認、現調前情報の回収、案件台帳への反映、未対応通知、見積後3回のフォロー、KPI計測です。ただし、すべてを一度に変えるのではなく、最も取りこぼしを確認したい対象フロー1本に絞ります。

## 最初に可視化する業務

現在の問い合わせを一件ずつ追い、受付から受注・失注までに使っている情報を洗い出します。最低限、次の項目を同じ場所で確認できるようにします。

| 管理項目 | 確認する内容 |
| --- | --- |
| 受付日時 | 問い合わせを受け付けた日時 |
| 流入元 | Webフォーム、電話など実際に利用している受付経路 |
| 顧客情報 | 氏名、連絡先など対応に必要な情報 |
| 相談対象 | 外壁、屋根、水回りなど相談の対象 |
| 希望時期 | 顧客が伝えた検討・工事時期 |
| 担当者 | 現在の対応責任者 |
| 案件状態 | 受付、現調調整中、見積作成中、見積提出済みなど現在地 |
| 次回行動日 | 次に連絡・確認する予定日 |
| 最終接触日 | 最後に顧客と連絡した日 |
| 失注理由 | 失注が確定した場合に確認できた理由 |

案件状態の名称は、実際の営業工程に合わせて決めます。大切なのは、名称の細かさではなく、担当者が変わっても同じ意味で使えることです。「対応中」のように次の行動が分からない状態は避け、次回行動日とセットで管理します。

問い合わせ前の導線に課題がある場合は、[ホームページを作ったのに問い合わせが来ない理由](/knowledge/web/homepage-toiawase-konai/)もあわせて確認してください。

## 実装手順

### 1. 対象フローと開始・終了地点を決める

対象は「新規問い合わせを受け付けてから、見積後フォローを完了するまで」のように一本で定義します。開始地点と終了地点が曖昧だと、どの案件を集計するかが担当者ごとに変わります。

### 2. 受信確認と担当者の初回返信を分ける

受信確認は「問い合わせを受け付けた事実」と「次にどのような連絡をするか」を伝えるものです。現地を確認していない段階で、金額・工法・工期を確約しません。

一方、初回返信は担当者が相談内容を確認して行う対応です。受信確認が送られたことだけで、担当者の対応完了にしないルールが必要です。

### 3. 現調前情報の回収項目を決める

現地調査の前に確認する情報を一覧にします。相談対象、所在地、希望時期、連絡しやすい方法、写真の有無などが候補になります。ただし、必要な項目は工事種別と会社の運用によって異なります。不要な個人情報まで集めず、取得目的と保存先を確認して決めます。

### 4. 案件台帳へ反映し、完了条件をそろえる

各工程について「誰が」「何を入力したら」「次の状態へ進めるか」を決めます。たとえば現調前情報の回収なら、必須項目を会社側で定義し、不足している場合の担当者と次回行動も決めます。

特定のサービスや画面を前提にせず、現在利用している環境で管理可能かを先に確認します。道具を変える必要がある場合も、業務ルールを固めてから選びます。

### 5. 未対応通知の条件を決める

未対応通知は、会社ごとに定めた基準時間を超えても担当者・案件状態・次回行動日のいずれかが未設定の案件を見つけるために使います。通知先、基準時間、営業時間外の扱い、通知を止める条件は設計時に決めます。

### 6. 見積後3回のフォローを設計する

見積提出後に確認する内容を3回分用意します。送信間隔、文面、連絡手段、停止条件は会社ごとに合意し、顧客から返答があった場合や担当者が個別対応へ切り替えた場合の扱いも決めます。

価格、工法、契約条件に関わる文章は自動確定せず、担当者が内容を確認できる工程を残します。

## KPIの定義と見方

数値は成果を保証するものではなく、どこで対応が止まっているかを確認するための判断材料です。集計期間と対象案件の定義を固定し、同じ条件で比較します。

| KPI | 定義 |
| --- | --- |
| 初回返信時間 | 問い合わせ受付日時から、担当者が最初に返信した日時までの時間 |
| 未対応数 | 会社が定めた完了条件を満たさず、基準時間を超えた案件数 |
| 次回行動日設定率 | 対象案件のうち、次回行動日が設定されている案件の割合 |
| 追客実施率 | 見積後フォローの対象案件のうち、設計したフォローを実施した案件の割合 |

率を見るときは、分母となる対象案件数も同時に確認します。問い合わせ件数が少ない期間の割合だけで良否を決めず、止まっている案件の中身まで確認します。

## 自動化しない判断

次の判断は、担当者または責任者が内容を確認する前提にします。

- 現地確認を伴う工法・施工可否の判断
- 金額、値引き、支払条件の確定
- 契約内容や保証範囲の説明
- クレーム、事故、緊急性がある相談への対応
- 個人情報を外部サービスへ渡す判断
- 顧客の意向が不明な状態での継続連絡

自動化は、人の判断をなくすことが目的ではありません。定型作業と確認漏れを見つける工程を仕組みに任せ、人が判断すべき案件を明確にするために使います。法務・個人情報の扱いに迷う場合は、運用開始前に専門家へ確認してください。

## 向いている会社・先に別課題へ取り組む会社

問い合わせ管理の整備が向いているのは、受付経路が複数あり、案件の担当者や次回行動を一覧で確認できない会社です。見積提出後の連絡方法が担当者任せになっている場合や、失注理由を振り返れない場合も対象になります。

一方、問い合わせ自体がほとんどなく、受付後の対応状況を確認する案件がない場合は、先に集客導線を見直します。[中小企業のWeb集客を始める順番](/knowledge/marketing/web-shukyaku-nani-kara/)を参考に、誰に何を提供するか、サービスページと問い合わせ導線がつながっているかを確認してください。

また、対応責任者を決められない状態では、通知を増やしても処理先がありません。先に役割と承認者を決めてから実装へ進みます。

## まとめ

- 問い合わせは一つの案件台帳に集め、担当者・案件状態・次回行動日を管理する
- 受信確認と担当者の初回返信を分け、対応完了の条件を決める
- 対象フロー1本に、現調前情報の回収、未対応通知、見積後3回のフォローを組み込む
- 初回返信時間、未対応数、次回行動日設定率、追客実施率を同じ定義で計測する
- 金額・工法・契約・クレーム・個人情報は人が確認する境界を残す

シクミベースの[見積フォロー漏れ診断](/diagnosis/reform-lead/)は税別55,000円です。現在の受付から見積後フォローまでを確認し、実装対象と優先順位を整理します。実装契約時には診断費を実装費から控除します。

診断後の実装範囲は、[リフォーム反響OS 30](/service/reform-lead-os/)で確認できます。売上・受注数・SEO順位を保証する商品ではなく、対象フロー1本を運用できる状態にするための支援です。
